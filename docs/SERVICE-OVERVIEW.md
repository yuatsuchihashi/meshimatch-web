# MeshiMatch サービス概要(正式版)

_起草: Kai / 2026-07-12 コミット。**本文書は以後の全設計の上位文書**。仕様書(spec-survey-ranking-v3.md)・R6計画等はここに従属する。_

## 1. サービス概要

MeshiMatch (meshimatch.com) は、グループの食事会における「お店決め」を解決するWebサービス。

**解決する課題:**
- **Cost to make decisions** — 店決めにかかる時間・調整コスト
- **Fear of making decisions** — 決定責任への恐怖。外したら幹事のせいになる
- **Fear of saying your own opinions** — 希望を言い出しにくい(アレルギー、予算、気分)

**解決の方向性:** fast, fun, fitting

**コア価値:** 候補を出すだけでなく**「決定まで完了させる」**こと。既存サービス(食べログ等)は候補提示まで。決める摩擦を残さない点が差別化。**「アプリが決めた」形式にすることで、誰の意見も否定されず、心理的安全性が保たれる。**

**主な仕組み:**
- 幹事だけが登録し、メンバーはリンクから登録不要で回答
- 希望(エリア・予算・アレルギー・苦手・気分)を匿名収集(見えるのは運営のみ)
- 希望の重なりから店を提案し、○×で決定
- 決定後は「チケット」(日時・店・メモを1枚に集約)として演出
- 無料・アプリ不要・日英対応

## 2. ターゲットユースケース(2シナリオ)

**シナリオ1: 対面・今すぐ(今夜このあと)** — 複数人でその場で悩んでいる。1台のスマホを回すかグルチャにリンクを送ると店が決まる。
→ **リアルタイム空席の問題があるため優先度は低。**

**シナリオ2: オンライン・未来の予定** — グルチャに送られたリンクからサーベイに回答すると店が決まる。予約前提なので「待たずに座れる」が保証しやすい。新しい店の発見体験もあると良い。
→ **こちらから着手。** 質のコントロールがしやすく空席問題を回避できる。

## 3. 最重要課題: お店の質保証

**問題の構造:** 人が決めた場合は「まぁまぁでも仕方ない」で済むが、**システムが決めた場合は外れが許されない**。1回変な店を出したら信頼が終わる。単純なスコア足切り(Google 4.0以上等)では不十分(「1 review, 5 stars」問題)。

### (a) センスのアルゴリズム化

再現したいのは「お店選びが上手い人のセンス」。評価軸: 値段感・雰囲気・ごはんの美味しさ・サービス。

創業者自身の選び方(教師データの元):
- レビュー数×星のクロス判定 → **ベイズ平均**で再現
- 写真の雰囲気 → **VLM・LLM**で「グループ向き/清潔感/騒がしさ」等をスコア化
- 値段感 → 価格帯×グループ予算の突合
- レビューテキストの行間 → **LLMで低評価の種類を分類**(「接客が悪い」は重く、「混んでた」は軽く)

構築手順: 創業者が30店程度を**良い/普通/ダメ**でラベル付け → 各店のGoogle Placesデータ(星・件数・写真・レビュー・価格帯)をLLMに渡しスコア化 → ラベルと突合してプロンプト調整・一致率向上。

**評価軸の注意:** ユーザーは「グルメな人」ではなく**「失敗したくない幹事」**。軸は「外れないか」「グループで使えるか(席の広さ・大人数可・騒がしさ)」に固定。味の絶対評価に寄せない。

### (b) 公式ユーザー(キュレーター)制度

信頼できるユーザーを公式ユーザーとして招き、推薦の母数を作る。少数の信頼できる人の推薦は匿名大量レビューより外れにくい(Yelp Elite、初期食べログと同構造)。「友達のおすすめ」という世界観と一貫。エリアを絞れば少人数で密度が出る(渋谷・恵比寿なら20人で数百店)。

設計課題: インセンティブ設計(称号→食事補助→収益シェアの段階)、質の定義、カバレッジ不足時のハイブリッド表示。

### (c) ループ構造

アルゴリズムがスコアを出す → 公式ユーザーが検証 → その判定でアルゴリズムを改善。(a)(b)を教師データ供給の関係で接続する。

**初期検証:** 恵比寿1エリア + 公式ユーザー10人程度から。

## 4. データ戦略

**Google Places API のみで構築(食べログ非依存)。**

理由:
- 創業者自身がGoogle Mapsのみで店選びできている(必要シグナルが揃っている証拠)
- 星・レビュー数・写真・レビューテキスト・価格帯が取得可能
- 食べログはAPI非公開・スクレイピングは規約違反リスク

制約と対処:
- レビューは1店あたり最大5件 → LLM分類と組み合わせる
- 取得データの長期保存に規約制限 → **place_id は保存可・詳細データは都度取得**の設計

補完候補: ホットペッパーAPI(無料、店舗基本データ。レビューは弱い)※現行実装では完全撤去済み。再導入はKai判断事項。
