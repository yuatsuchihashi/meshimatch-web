## 1. 実装分割案(1ラウンド=1ワーカー、既存ゲート適用)

### R6a — Google Places データ基盤(機械的・先行可能)
- Places API 統合レイヤ: **place_id は保存可・詳細は都度取得**の規約準拠設計。既存 `supabase/012_places_cache.sql` と `src/lib/google-places.ts` を土台に、キャッシュTTL・取得フィールド(星・件数・価格帯・写真ref・営業時間・**レビュー最大5件**)を確定
- 恵比寿1エリアのシード: Text Search で飲食店の place_id 一覧を取得しレストラン行を生成(**自己登録禁止と矛盾しない**: これは候補プールではなく「質評価対象のカタログ」。プール供給は従来どおり人間の推薦のみ)
- 営業時間の自前供給(v3.3 §3-4)の gmaps_import 経路がこの基盤に乗る

### R6b — センスのアルゴリズム化(スコアリングパイプライン)
- オフラインバッチ(scripts/)として実装。入力=R6aのカタログ、出力=店ごとの内部スコアとタグ:
  1. **ベイズ平均**: 星×件数(少件数店の過大評価を抑制)
  2. **LLMレビュー分類**: 5件/店を分類し重み付き減点 — 「接客が悪い・不衛生」は重く、「混んでた・行列」は軽く。カテゴリ設計はラベリング(R6c)と突合して調整
  3. **VLM写真雰囲気スコア**: 「グループで使えるか」軸(席の広さ・卓の形式・騒がしさの見た目)中心
- 出力スキーマ: `hazure_risk`(内部)+ `group_fit_tags`(可視チップ候補: 個室あり気配/大人数向き/静か等)
- モデル選定・コストはKai判断(§3)。実装時に最新のモデル/価格を確認して提示する

### R6c — 創業者ラベリングツール(簡易)
- dev専用ページ `/labeling`(ローカルのみ): 恵比寿カタログを1店ずつ表示(写真・星・件数・レビュー5件)→ **良い/普通/ダメ の3ボタン**+一言メモ → JSONL保存
- 評価スクリプト: エンジン出力 × Kaiラベル30店の突合(混同行列+不一致店の理由表示)→ プロンプト/重みの調整ループ
- 目標の初期案: **「ダメ」店の検出再現率を最優先**(外れ回避が核のため。過剰に厳しい誤検出は許容)

### R6d — キュレーター制度の運用設計(実装最小)
- R5実装済みの基盤(認証バッジ・公開リスト・PRラベル・サーバー強制)をキュレーター制度として運用に乗せる
- 恵比寿パイロット: キュレーター10人規模。バッジ付与はv1手動(実装済み)のまま
- 段階インセンティブ(称号→食事補助→収益シェア)は**Kai判断事項**として§3に整理。実装はバッジ表示のみで開始可

依存関係: R6a → R6b/R6c(並行可) → 突合調整 → R6d運用開始。UIへの反映(候補カードへの group_fit チップ表示)は小ラウンドとして後続。

## 2. 初期検証(恵比寿パイロット)

- 範囲: 恵比寿1エリア、キュレーター10人、Kaiラベル30店
- 合格基準の初期案: Kaiラベル「ダメ」の店をエンジンが上位提案に混入させない(再現率目標はラベル完了後に設定)
- レビュー5件/店・詳細都度取得の制約下で成立することを確認

## 3. Kai判断事項リスト

| # | 判断 | 補足 |
|---|---|---|
| 1 | Google Cloud 課金設定とAPI予算上限 | Places API は従量制。恵比寿シード+都度取得の月額目安はR6a着手時に試算提示 |
| 2 | LLM/VLMのモデル選定とコスト許容 | 実装時に最新モデル・価格で選択肢を提示(レビュー分類は軽量で足りる可能性大) |
| 3 | ラベリング30店の選び方 | 恵比寿でKaiが実体験のある店を優先か、エンジン出力からサンプリングか |
| 4 | キュレーター10人の候補 | 声かけリストと打診文はKai側 |
| 5 | インセンティブ段階の初期値 | 称号のみで開始→食事補助の条件→収益シェアの料率、の段階設計 |
| 6 | 「外れないか」の見せ方 | 推奨: 数値・ラベルとも非表示、ダメ店は**そもそも出さない**+良側は group_fit チップで示す(点数非表示原則と整合) |

## 3.5 live有効化チェックリスト(R6aレビューで確定したゲート)

`--live` / `GOOGLE_PLACES_LIVE=1` を有効化する前に必ず:
1. **P1**: 既存のlive経路 (`src/lib/restaurants/enrich.ts`, `/api/restaurants/manual`) が Google の `rating` を `restaurants` に長期保存している — `fetchDetailsWithCache`(places_cache+TTL)経由に付け替え、rating等の揮発フィールドの長期保存を止める
2. Google Places ToS のキャッシュ/保存制限を、シードが保存する識別系フィールド(名称・住所・座標・価格帯)について確認
3. API予算上限の設定(Kai判断#1)
4. 小物: reviews 5件capのテスト追加、openNow のフィールドマスク修正(currentOpeningHours)
