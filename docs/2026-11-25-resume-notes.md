## 現在のプロダクトと合意

- 対象は `yuatsuchihashi/meshimatch-web`。単独の `index.html` ではなく、Next.jsのアプリ本体で作業する。
- 現在の試作は、集合エリアを幹事が設定してから、参加者が好みを回答し、最大3店を比較・投票する流れ。
- カフェとレストランで質問を分けている。幹事の用途は「食事」「カフェ・軽食」の2つ。「どちらでも」は新規設定から外してある。
- カフェのアンケートはユーザーから概ね了承済み。回答フローを土台として維持する。
- レストランは料理ジャンルに加え、静かさ・にぎやかさ、待ち時間、口コミ評価、距離、価格を扱う。
- 店舗ジャンルと料理メニューのカテゴリを分けている。例としてイタリア料理とピザは店舗分類、パスタはメニューから判定する。
- 必須条件は各人が注文できる料理・注文の存在を先に確認する。好みの高評価で必須条件の不一致を埋め合わせない。
- 候補の評価は非公開で「行ってもいい」「もう少し知りたい」「今回は難しい」。全員の承認が重なる候補を決める。
- ローカル試作は33店・94メニューの架空DB。新宿とブエノスアイレスを用意している。実在店の検証済み情報ではない。

### 写真の扱い

全て架空DB用のAI生成イメージ。実店舗や実メニューの写真と誤認させない表示が必要。
写真から原材料、アレルギー、ベジタリアン対応、辛さ等を判定しない。
対応不明のメニューに別の料理の写真を適当に当てない。
実店舗の写真を扱う段階では、提供元・利用条件と対象店舗／メニューとの対応を確認する。

## 追加アイデア — 記録のみ、実装しない

### 1. 場所が決まっていない場合の調整

ユーザーの意図

現状のアンケートは場所が決まっている前提。場所自体が未定でも調整できるようにしたい。

後で整理する論点

- 「場所」は集合駅・エリアの意味か、各人の出発地も含むか。
- 各人が行ける範囲や移動負担をどう把握するか。
- エリアを先に決めるか、お店の候補と一緒に決めるか。
- 既存の食事の好みアンケートへ、いつつなげるか。

現時点では新しい質問や調整ロジックを追加しない。

### 2. 日程が決まっていない場合の調整

ユーザーの意図

日程未定なら、日程を決めるところから支援したい。

後で整理する論点

- 日付だけが未定か、時間帯や滞在時間も未定か。
- 日程・場所・お店のどれから決めるのが自然か。
- 各人の参加可能日と、店舗の営業時間・空席確認をどう区別するか。

現時点ではカレンダーや日程アンケート等を追加しない。

### 3. おすすめのお店をリンクで共有

ユーザーの意図

アンケートの基本は今の形でよい。一方、参加者におすすめのお店があるなら、リンクを入れて共有できるようにしたい。
ユーザーは「そっちを優先するべきな気もする」と考えている。

まだ確定していない点

- 「優先」は、この機能の開発順を上げる意味か、共有されたお店を候補として優先する意味か、その両方か。
- 共有を幹事だけがするか、全員がするか。
- 店舗DBにまだないお店も候補にできるようにするか。
- 共有された店とアンケートからの推薦候補を、どう一緒に比べるか。
- リンク先の情報が不足する場合、必須条件が未確認であることをどう示すか。

リンク入力・リンク先情報の取得・候補の優先処理は実装しない。
「推薦の前に、既に行きたい店があるかを受け止める」という方向も、次回の対話で整理するための仮説として残す。

## ローカル実行の再開方法

プロジェクトディレクトリは `meshimatch-web/`。
PCを閉じた後もサーバーが動き続けるとは限らない。

```bash
MESHIMATCH_LOCAL_MODE=1 NEXT_PUBLIC_MESHIMATCH_LOCAL_MODE=1 NEXT_DIST_DIR=.next-build npm run build
MESHIMATCH_LOCAL_MODE=1 NEXT_PUBLIC_MESHIMATCH_LOCAL_MODE=1 NEXT_DIST_DIR=.next-build npm run start -- --hostname 127.0.0.1 --port 4317
```

開始画面は `http://127.0.0.1:4317/instant`。
候補一覧は `/instant/top3` だが、同じブラウザ内に回答済みセッションが必要。
今回の未検証の下準備を含めて再開する場合、型検査・テスト・ビルドを確認してから利用する。
開発サーバーは以前ファイル監視の上限で不安定になったため、直近は本番ビルドをローカル起動していた。
