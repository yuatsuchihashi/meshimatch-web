# エリア調整 v1

2026年11月26日。日程調整に続き、エリア決定済み／みんなで調整したい、の分岐と調整アンケートをアプリ本体へ実装。

11月27日の追加要件として、出発地点・帰りや次の目的地・実経路の所要時間・主要駅以外の発見を考慮する設計案を `docs/area-access-design.md` に整理した。以下は現在実装されているv1の説明であり、新案はまだ画面へ反映していない。

## 入口

`/instant` に「集まる場所は決まってる？」の2カードを置く。最初は未選択。

| 選択 | 表示するもの | 次の行動 |
|---|---|---|
| 決まっている | 既存の集合エリア・半径、人数、食事／カフェ | お店のアンケートを始める |
| みんなで調整したい | 東京／BA、人数、食事／カフェ | エリアのアンケートを作る |

日程調整からの日時・人数は両分岐へ引き継ぐ。エリアの調整中には未定のareaIdを既存のお店アンケートへ渡さない。

## 回答フロー

1. 共有リンク `/area/<id>` から回答する。ログイン不要。同じ端末で別の人の回答も追加できる。
2. 「集まれるエリア」を複数選ぶ。
   - 未選択を「どこでも」とみなさない。
   - 「この一覧ならどこでも大丈夫」は、表示中の候補すべてへの明示的な回答。
   - 「この一覧に行けるエリアがない」も回答として保存できる。未回答とは別に扱う。
3. 行けるエリアの中で「特に行きたい場所」を任意で最大2つ選ぶ。表示名も任意。
4. 全員回答後に、全員の行けるエリアの共通部分を候補として出す。
5. 共通候補内では希望票の多い順に並べる。同数の場合はカタログ順。移動時間の良し悪しを表す順位ではない。
6. 幹事が候補からエリアを決定する。
7. 選択したエリア・人数・用途を `/instant?area=<id>` へ渡し、既存のお店アンケートを新しいセッションとして開始する。

共通候補がゼロなら、行ける範囲を勝手に緩めず、回答の見直し・相談へ戻る。
回答一覧と希望は参加者へ公開。飲食の個人アンケートの非公開の扱いは変更していない。

## 交通データと質問の関係

実際の経路・交通時間APIは未接続。したがって、出発駅・交通手段・片道上限を入力させて、架空の所要時間で合否を判定しない。
今回の可否の根拠は、本人による「行けるエリア」の申告。
実交通時間が取得できるようになったら、各自の上限内に限定し、最大の移動負担を小さくする順に提案する案へ発展できる。

## カタログと架空店舗

- 調整候補は都市内で分離。東京10エリア、BA5エリア。
- 全15エリアに、お店選びへ進むための架空DBを用意した。合計111店舗。
- 新宿19店舗とBA中心部14店舗の既存データは変更していない。
- 新規13エリアは各6店舗。新規店名に「サンプル」を付け、メニューは既存の合成レシピから構成する。
- エリアの座標は試作用の検索基準点。実店舗の場所や移動時間を保証するものではない。
- 未対応のエリアを新宿にすり替える処理はない。

## 保存と権限

- ローカル限定API `/api/area-polls`、`/api/area-polls/<id>`。
- `.localdb/area-polls/<id>.json` に永続保存。編集のハッシュは公開レスポンスへ含めない。
- 幹事だけが確定・再開でき、回答の編集は回答ごとの秘密キーで制御する。
- 同じ回答IDの再送・編集で人数を増やさない。
- 確定後は回答を固定し、幹事が再開してから変更する。
- 日程連携がある場合は、確定日程の候補IDと人数を作成時に保存。回答・確定の両方で再照合する。
- 日程変更後は古い回答で確定できない。履歴は読めるが、新しい日程の調整を作り直す。
- エリア確定から戻った後は、エリアと参加人数を固定する。見直す場合はエリア調整画面へ戻る。

ローカルの共有リンクは同じPCを指す。別端末から使うための外部公開は今回行っていない。
