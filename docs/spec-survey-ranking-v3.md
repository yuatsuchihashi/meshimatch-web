# 仕様書: 2モード化 + Survey再構成 + お店中心ランキング v3.2

_状態: 確定(R1着手GO済み) / 起草: 2026-07-09, 2モード改訂: 2026-07-10, Kai判断反映(v3.2): 2026-07-10 Chief(Fable)_

## 0. 確定済みの前提(Kai決定)

- マッチ度(点数)のUI表示は廃止済み。順位付けは内部処理のみ、ユーザーには**理由**を見せる
- 候補となる店は「信頼できる人間のおすすめ」のみ。**外部DB(HotPepper等)から新しい店を探すことはしない**
- **店舗の自己登録は禁止**(明文の禁止事項。店舗関係者による自店の登録・自薦を規約レベルで禁止する。質の担保が理由)
- 公式アカウント(インフルエンサー): 公開おすすめリストで候補プールを補充。売名(自己プロモ)⇔信頼できる店カード、のギブアンドテイク
- **店決めフローは2モード**: 「今からごはん(即時)」と「予定を組む(計画)」(2026-07-10 追加)
- **HotPepper API は完全撤去**(検索・ランキングだけでなく写真・営業時間等のメタ補完も使わない。2026-07-10 Kai確定)
- **公式アカウントは「ブルーバッジ(認証)」モデル**: 招待制/申請制ではなく、実績が立ったアカウントに認証を与えるメリットベース(2026-07-10 Kai確定)
- **PR/広告は最初から許可**。ただし PR ラベル必須 + ランキング減点(2026-07-10 Kai確定。推奨の「v1禁止」は不採用)
- **即時モードの現在地は駅ピッカー**で取得(2026-07-10 Kai確定)

## 1. 利用モード — 即時 / 計画

### 1-1. モード比較(設計の芯)

| 観点 | 即時モード「今からごはん」 | 計画モード「予定を組む」 |
|---|---|---|
| 位置づけ | **新規フロー** | **既存フローの正式名称**(現行アプリ≒計画モード) |
| アクセス評価の基準点 | **現在地 = 駅ピッカーでワンタップ選択**(確定。ジオロケーションは使わない) | プロフィール既定の出発地(survey でワンタップ確認・当日変更可) |
| 営業状態 | **営業中(今+滞在想定90分)がハードフィルタ必須級**。営業時間が不明の店は除外せず「営業時間 要確認」バッジ+地図リンクで正直に出す(HotPepper撤去により**不明店が多数派の前提で設計** → §3-4) | 開催日の定休日チェック(分かる範囲で)。不明は同様にバッジ |
| survey | **最軽量: 気分(必須)+ NG確認(プロフィール既定の表示のみ)**。それ以外は聞かない | §4 の再構成 survey(気分+任意項目) |
| 参加者 | **「今いる/来られる」確定メンバーだけで回す**。全員回答待ちをしない — 回答した人の分だけで即ランキング | 招待リンクで揃うのを待てる。未回答者がいても部分回答でランキング可(現行仕様を踏襲) |
| 意思決定 | **未確定(Kai保留)**: 幹事即決 vs 簡易○×投票。R4着手前に画面フロー2案のUX比較を用意してKai相談にかける。時間目標 **作成→決定3分以内** は両案共通の制約 | 余裕のある○×投票→決定(現行フロー) |
| 距離の重み | **w_access を大きく**。ゾーン距離≤1(同一/隣接)を強く優遇、遠い候補は原則沈む | 標準の重み。「いちばん遠い人」基準 |
| 日時 | 常に「いま」。日程調整なし | **日時決め→店決めの順**(§1-3) |
| チケット | 決定と同時に当日チケット生成(同機能) | 決定時にチケット生成(現行) |

### 1-2. エントリポイントUI

- グループ作成の最初の画面を**2枚の大きな選択カード**にする: 「🍜 今からごはん」「📅 予定を組む」(チケット風カード、既存デザイン言語)
- 即時モードはグループ名入力をスキップし自動命名(例: 「7/10 の今夜ごはん」)。作成→現在地ワンタップ→気分ワンタップ→候補、の3画面で完結させる
- ホームの「グループを作ろう」カードのタップ先がこの分岐になる。既存グループからの「今から集まる?」再利用は将来検討(§7)

### 1-3. 計画モードと日程調整の関係(提案: 日時先行)

**「日時を先に決めてから店決め」を正とする。**同時進行にしない理由:
1. 参加者が日時で変わる → 参加者が変わるとプール(誰のおすすめか)もアクセス公平性も変わる。店を先に/同時に決めると手戻りが構造化されてしまう
2. 定休日・予約可否のフィルタは日付が確定して初めて意味を持つ
3. 日時×店の同時投票は選択肢が積で増え、「決める面倒を消す」という核に反する

v3.1 では日時決めは現行どおり幹事入力(候補日の調整機能は本仕様の範囲外、将来 §7)。

### 1-4. ランキングへの影響 — 土台は共通、重みだけ変える

信頼の輪ラダー(§2)・ハードフィルタ・理由バッジの仕組みは**両モード完全共通**。モードが変えるのは:
- 重みプリセット: `RANKING_PRESETS = { instant: {...w_access大, 営業中hard}, planned: {...標準} }`
- アクセス基準点(現在地 vs プロフィール出発地)
- 意思決定UI(幹事即決 vs ○×投票)

エンジンを2つ作らない。分岐はプリセットと入力の差だけに閉じ込める。

## 2. 候補プール — 信頼の輪ラダー(両モード共通)

候補は以下の順に外側へ広げて集める。**検索による補充は行わない。**

| Ring | 供給源 | 信頼の重み |
|---|---|---|
| 0 | グループメンバー本人のおすすめ・お気に入り・survey「行きたい店」投入 | 最強 |
| 1 | メンバーのつながり(フォロー/友達)の公開お気に入り | 強 |
| 2 | メンバーがフォローする公式アカウントの公開おすすめリスト | 中 |
| 3 | (なし) 空状態 + 貢献導線 | — |

Ring 3 の空状態は誤魔化さない: 「このあたりのおすすめ、誰かある?」とメンバーに聞き返す(既存「行きたい店を足す」を器に)。即時モードで空のときは「近くで営業中のおすすめが見つからない」と正直に表示し、条件緩和(距離をひと駅広げる)の提案だけ行う。

## 3. ランキング仕様(両モード共通の土台)

### 3-1. ハードフィルタ(足切り・点数化しない)

- アレルギー・食事制限に抵触する店
- グループ予算上限の明確な超過
- 【即時のみ】営業中でないことが判明している店(不明は除外しない → バッジ)

### 3-2. スコア(内部のみ。UI非表示)

```
score = w_rec × 推薦の強さ + w_pref × 選好適合 − w_access × アクセス減点
※ w_* はモード別プリセット(§1-4)
```

- **推薦の強さ**: Ring序列(0 > 1 > 2) + 複数人が推している場合の加点
- **選好適合**: ジャンル・気分・予算感のマッチ(プロフィール既定値 + survey差分)
- **アクセス減点**: 各メンバーの基準点(即時=現在地 / 計画=出発地)→店の最寄りゾーンの粗い距離。集約は**最悪値(いちばん遠い人)**。v1 ゾーンは `areas.ts` 由来の約20ゾーンで開始。**回答には駅(ピッカーの選択値)を生で保持し、ゾーンへの解決はランキング時に行う** — ゾーンマスタの粒度を後から変えても過去データがそのまま追随する構造(Kai指示: 粒度は後から変更可能に)
- **距離で足切りしない**(即時モードでも減点強化に留め、遠い店は「少し遠いけど◯◯さんの推し」と理由付き)
- **PR減点**: `pr = true` の推薦はスコアを一律減点し、非PRの同等候補より下に並ぶことを保証(§5)

### 3-3. カード表示(点数の代わりに理由)

- 推薦バッジ: 「◯◯さんのお気に入り」「◯◯(公式)のおすすめ」
- **PRラベル**: PR推薦のカードには「PR」バッジを必ず表示(非表示にする設定は作らない)
- 理由タグ例: 「全員30分圏内」「予算内」「いま営業中」「◯◯さんと◯◯さんが両方推し」
- 理由文は候補ごとに固有化(現状の全カード同一文はこのラウンドで解消)

### 3-4. 営業時間・写真データの自前供給(HotPepper完全撤去の帰結)

外部APIによるメタ補完は行わない。供給源と優先順:

1. **推薦者の入力**(公式アカウントは推薦時に営業時間・定休日の記入を推奨、一般メンバーは任意)
2. **Google Maps リンクからの自動抽出**(店登録時にURLを貼ると Places API 相当の構造化データを取得 — 幹事DB構想の中核機能。LLM不使用)
3. **未入力は「営業時間 要確認」バッジ + 地図リンク**が既定の体験。データが薄い初期ほどこのバッジが多数派になることを許容する

各メタ項目には供給源(`member_input` / `official_input` / `gmaps_import`)と更新日時を記録し、後から上書き・検証できるようにする。

## 4. Survey再構成

原則: **事実と恒常的な情報はプロフィールに1回だけ。アンケートはイベント固有の差分だけ。**

| 項目 | どこで聞く | 即時モード | 性質 |
|---|---|---|---|
| アレルギー・食事制限 | プロフィール(初回) → surveyは確認表示のみ | 確認表示のみ | ハード足切り |
| 出発地(駅) | プロフィール(初回) → surveyは「いつもの場所から?」ワンタップ | **聞かない(現在地に置換)** | アクセス材料 |
| 好き嫌いジャンル・予算感 | プロフィール(初回) → surveyは差分だけ | 聞かない(既定値使用) | 選好スコア |
| 今日の気分・軽め/がっつり | survey(毎回) | **唯一の必須質問** | イベント固有 |
| 行きたいエリア | survey(任意・一言) | 聞かない | soft加点 |
| 行きたい店 | survey(任意) | 聞かない(候補画面から追加は可) | Ring 0 投入 |
| 希望ターミナル駅 | **聞かない** | 聞かない | 廃止 |
| 新店の検索条件 | **聞かない** | 聞かない | 外部検索なし |

**ゲスト(アカウントなし)**: 計画モードでは survey 内で アレルギー・制限(必須) / 気分(必須) / **出発地(任意 — Kai確定)** / 行きたい店(任意)。匿名ID(`mm_anon_id`)に紐付け、登録時に引き継ぐ。**即時モードのゲストには出発地を聞かない**(現在地=駅ピッカーが基準点になるため不要 — Kai確定)。その場に居る前提なので幹事の画面で人数に含めるだけでもよい(NG だけ口頭確認 → 幹事が代理入力できる「NG追加」チップを候補画面に置く)。

## 5. 公式アカウント仕様 — ブルーバッジ(認証)モデル(Kai確定)

**思想**: 招待制でも申請制でもなく、**実績が立ったアカウントに認証バッジを与える**メリットベース。誰でも公開リストは作れるが、「公式」の見た目と Ring 2 供給源としての露出はバッジ保持者だけが得る。売名(自己プロモ)⇔信頼できる店カード、のギブアンドテイク。

- **終着形**: 実績指標にもとづく自動/半自動認証
- **v1**: 実績データがまだ無いため**運営(Kai)による手動付与**。ただし基準は最初から明文化し、付与記録(いつ・誰が・どの根拠で)を残す

**バッジ基準の指標案**(v1では手動判断の参考値、将来は自動化の入力):
| 指標 | 意味 |
|---|---|
| フォロワー数 | 露出の裏付け(単独では不十分) |
| 候補採用率 | 公開リストの店がグループ候補に載った回数/リスト掲載数 |
| 決定貢献数 | 推薦店が最終決定まで至った回数 |
| お気に入り転載数 | 他ユーザーが推薦店を自分のお気に入りに追加した数 |
| 通報・削除歴 | ゼロであること(必須条件) |

**広告・PR(Kai確定 — 最初から許可)**:
- PR・提供案件の推薦には **PRラベル必須**。ラベル付き推薦はランキングで一律減点(§3-2)
- ラベル無しPRの検出・通報フローは**将来課題として明記**(v1では規約違反として手動対応)
- 違反時はバッジ剥奪を基本ペナルティとする

**禁止事項(明文・変更なし)**: 店舗関係者による自店の登録・自薦・公式アカウント化(店舗の自己登録は質の担保のため全面禁止)

## 6. 既存フロー・データモデルへの影響

- **既存フロー = 計画モード**。現行の招待リンク→survey→候補→○×投票→チケットはそのまま計画モードの本線。即時モードが新規追加
- **R1(データモデル)への波及**:
  - `groups.mode: 'instant' | 'planned'`(既存行は `planned` にバックフィル)
  - `survey_responses.departure_station`(**駅を生で保持**。即時=駅ピッカーの選択 / 計画=プロフィール既定 or 上書き。ゾーンへの解決はランキング時 — 粒度変更に強い。ジオ座標は**保存しない**)
  - `restaurants.opening_hours` ほかメタ項目 + **項目ごとの供給源・更新日時**(`member_input` / `official_input` / `gmaps_import`。§3-4。外部API列は追加しない)
  - 公式アカウント: `profiles.account_type: 'user' | 'official'` は廃し、**認証は `verification`(付与日時・付与者・根拠メモ)で表現**。実績指標(§5)を集計できるイベント/カウンタの置き場も確保
  - 推薦: `pr: boolean`(PRラベル。デフォルト false)
  - ゾーンマスタ: `zones`(id・名前・世代/バージョン) + `station_zone_map`(駅→ゾーン)。**マッピングの差し替えで粒度変更できる構造**(回答側は駅を持つため過去データも追随)
  - フォローは既存 `follows` を流用

## 7. 実装ラウンド分割(ワーカー委任単位・改訂)

| Round | 内容 | 主な対象 |
|---|---|---|
| R1 | データモデル: mode / departure_station / メタ供給源 / 認証 / pr / ゾーンマスタ | supabase migrations, localdb |
| R2 | プールビルダー + ランキングエンジン置換(重みプリセット2種、**HotPepper完全撤去**、PR減点) | `src/lib/recommendation/`, `matching-engine.ts`, results API |
