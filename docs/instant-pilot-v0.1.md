# MeshiMatch 即時モード実験 v0.1

_状態: 2026-08-02時点の実験用正本。即時モードについて過去文書と矛盾する場合、この文書を優先する。_

## 1. 実験で確かめること

2〜8人がその場で1台のスマホを回し、3分以内に「全員が行ってもよい実在店」を1店決めて、地図を開けるかを確かめる。

初期範囲は渋谷または恵比寿の1エリアに絞る。計画モード、予約連携、AI電話、全東京カバレッジは本実験の対象外。

## 2. 現在の確定フロー

1. 人数と位置利用の有無を決める。
2. スマホを回し、各自がWish・Avoid・食事制限を非公開で複数選択する。
3. 明確な条件衝突を除き、信頼プールから違いのある3店を出す。
4. 同じスマホを回し、各自が「行ってもよい店」を複数承認する。途中経過は見せない。
5. 全員終了後に一斉開票する。「どれも難しい」が最多票以上なら別の3店へ進む。
6. 最多承認店をチケット化し、地図・電話・共有へ進む。

同票は候補順位で決める。あとから来た人は回答を追加できる。

## 3. 実験プールの契約

入力先は `data/pilot-restaurants.csv`。30〜50店を登録する。

### 必須項目

| 列 | 内容 |
|---|---|
| `name` | 店名 |
| `area` | 実験対象エリア |
| `genre_id` | `G001`〜`G017` |
| `budget` | 1人あたりの目安。例 `¥2,000〜¥3,000` |
| `why_good` | グループ利用で外しにくい理由。内部推薦メモ |
| `address` / `place_id` / `map_url` | 少なくとも1つ |

### 推奨項目

| 列 | 内容 |
|---|---|
| `photo_url` | 店舗写真。利用権限を確認したURLのみ |
| `phone_number` | 電話確認ボタンに使用 |
| `access_note` | 例 `恵比寿駅徒歩4分`。実測または店舗表記のみ |
| `lat`, `lng` | 両方そろえて入力 |
| `open_now` | 実験時点の確認用。`true` / `false` / 空欄 |
| `opening_hours` | 人が確認した営業時間の短い表記 |

`why_good` は「おいしい」だけではなく、次の観点から具体的に書く。

- 2〜8人で話しやすい
- 価格が読みやすい
- 席・騒がしさ・注文形式がグループ利用に合う
- 初見でも外しにくい

店舗関係者の自薦、根拠のない営業時間・徒歩時間、無断転載画像は入れない。

## 4. 入力と取込

入力途中の確認:

```bash
node scripts/pilot-pool.mjs --allow-partial
```

30〜50店そろった後の正式検証:

```bash
npm run pilot:validate
```

ローカルDBへの取込:

```bash
npm run pilot:import-local
```

取込前のDBは `.localdb/db.json.bak-pilot-pool` に退避される。同じ店舗はPlace ID、または店名とエリアの組み合わせで同じIDになり、再取込では更新される。

ローカルモードでは実験用公式キュレーターが候補プールへ自動的に加わる。本番環境で有効にするときは `MESHIMATCH_PILOT_POOL=1` を設定し、同じプロフィール・認証・店舗・推薦行をSupabaseへ移す。現在の取込ツールはリモートDBへ書き込まない。

## 5. 計測イベント

即時モードでは以下を匿名IDとグループID単位で記録する。個人ごとの回答内容は送らない。

- `instant_started`
- `instant_answers_completed`
- `instant_candidates_shown`
- `instant_redrawn`
- `instant_ballot_completed`
- `instant_decided`
- `instant_map_opened`

ローカル実験の記録先は `.localdb/events.jsonl`。

## 6. 初期合格基準

まず5〜10組で使い、次を確認する。

- 90%以上のセッションでデモではない3候補が出る
- 回答開始から店決定までの中央値が3分以内
- 決定セッションの70%以上で地図が開かれる
- 候補不足・不正な営業時間・明らかな外れ店を個別に記録できる
- 利用後に「また使いたい」が過半数

数字は実験開始時の仮説であり、結果を見て更新する。
